hindsight

Entretien hors bande des Rule Files que vos agents chargent : un mod Claude Code et un CLI, rien dans le contexte de l'agent.

Le produit

Ce que fait hindsight

Vous corrigez Claude Code en session, et la même consigne revient d'une semaine à l'autre. hindsight écoute la fin de chaque tour, forke la session sur son propre cache quand cela en vaut la peine, garde vos mots comme preuves, laisse la récurrence trancher, puis vous propose des changements précis de vos Rule Files : AGENTS.md, CLAUDE.md, .claude/rules/, styles de sortie. Rien n'est écrit sans votre décision. Rien n'entre dans le contexte de l'agent.

Vous

Vous travaillez avec les agents, lisez les Proposals et décidez : accepter, modifier, rejeter avec une raison, ou confier à un Handoff.

L'agent de travail

Il fait sa tâche dans la session. hindsight ne lui ajoute jamais rien : pas de contexte, pas de texte dans les réponses de commande.

Le Debrief

Un fork de la session, servi par son propre cache, qui répond à cinq questions et rend des Notes. Il ne lance aucun outil et n'écrit aucun fichier.

hindsight

Le mod tient le Portail, le fork, la Notice et le panneau ; le CLI vérifie, stocke, fait tourner Learn et Prune, et exécute chaque Décision.

Le Portail décide en code, puis un petit modèle confirme

À la fin de chaque tour, le mod accumule les faits depuis le dernier Debrief de la session, applique les sauts directs dans l'ordre, puis pèse les signaux contre le seuil. Seulement si le code dit oui, un classifieur lit le brief et vos trois derniers messages et répond debrief ou skip. Chaque décision part au journal, ce qui permet de rejouer le Portail sur vos transcripts passés et de calibrer le seuil.

Le simulateur fait tourner le code du dépôt (src/domain/gate.ts, facts.ts, human.ts) avec la configuration par défaut.

Le Debrief : cinq questions, vérifiées mot pour mot

Le fork reçoit la dernière requête du fil principal avec le prompt ajouté : même modèle, même système, mêmes outils, tous refusés. Son préfixe vient donc du cache de la session, et hindsight mesure quelle part : sous le plancher, le Debrief est en erreur et aucune Note n'est gardée.

  1. Vos éditions ont-elles rendu une Loaded Rule fausse ? Propose la correction.
  2. Une nouvelle Rule mérite-t-elle sa place ? Énonce-la.
  3. Quelle Loaded Rule t'a gêné, induit en erreur, ou as-tu dû enfreindre ?
  4. Qu'as-tu dû deviner faute de Rule ?
  5. Qu'a corrigé l'humain : une habitude ou un cas unique ?

La question 1 donne des Stale Rules, les questions 2 à 4 des Observations, la question 5 des Steers. Le CLI relit le transcript avant de stocker quoi que ce soit : une Quote doit figurer mot pour mot dans un de vos messages, une Observation doit correspondre à un appel d'outil réel, une Stale Rule à une édition réelle que le fichier porte encore.

La vérification ci-dessous fait tourner parseDebrief et containsVerbatim du dépôt ; les textes sont synthétiques et modifiables.

Learn pèse la récurrence, le code compte

Learn part tout seul, hors bande, quand un Debrief fait passer les Notes en attente au-dessus du seuil de la configuration, et qu'assez de temps a passé depuis le passage précédent. Un appel claude -p --json-schema sur Opus par dépôt, sous budget, sans modèle de repli : un modèle plus faible qui propose des règles vaut moins qu'aucune proposition. Le modèle regroupe et rédige ; le code garde la main sur ce qui compte.

La Review : vous décidez, hindsight applique

À votre session suivante, une ligne de statut dit combien de Proposals attendent. /hindsight review ouvre le panneau : une passe de quelques Proposals (review.pageSize), triées par Prevalence puis par âge, une par écran. Chaque Quote s'ouvre sur votre message entier, secrets masqués. Les décisions vivent dans le CLI, derrière un seul port : le panneau dessine et renvoie ce que vous pressez.

Le panneau ci-dessous est une maquette : le diff vient de unifiedDiff, les états de nextProposalState, le masquage de redactSecrets.
